## What I built beyond the plan's literal text

The plan was written in one pass and never executed (per the previous handoff). Following
its own instruction — "fix it and keep going, keep the tests honest, note what you
changed" — I found and fixed real bugs along the way rather than treating the plan as
gospel. All in `slp-tracker.html`, all covered by the tests that exposed them:

- **Test harness (Task 1):** three bugs in the harness itself, not the app — (1) the TAP
  runner IIFE read the empty `TESTS` array before later `<script src="*.test.js">` tags
  had executed, now deferred to the `load` event; (2) a missing target file made the
  iframe navigate to a `chrome-error://` page, and reading `w.SLP` across that origin
  boundary threw *after* the load timeout was already cleared, hanging forever — now
  wrapped in try/catch; (3) `window.close()` is blocked because the harness page is the
  initial navigation target, not one opened by script, so the process never exited on its
  own — the runner now polls the log and kills Chrome itself instead of waiting.
- **`ui.shell` render scheduler (Task 8), the big one:** a click handler that writes to
  the store and then calls its own `SLP.ui.render()` can race a caller's own explicit
  `render()` call made right after triggering the click — a plain FIFO queue wasn't
  enough, because a caller could still be handed the result of an *earlier* link in the
  chain while a newer render (from the handler, once its write landed) started clearing
  the DOM moments later. Replaced with a coalescing render loop: every `render()` caller
  now waits for the loop to reach quiescence, so if another render gets requested while
  one is in flight, the loop runs again before anyone is told it's done. This showed up
  first as a fully-reproducible failure (3/3 runs) in a schedule-view test and, once
  fixed, made several other suites (students, today) pass cleanly on the first
  implementation attempt — it was clearly going to bite repeatedly otherwise.
- **The `Alt+A` save-queue race (Task 11):** the same *shape* of bug in a different place
  — the keydown handler did an async `planForDate()` lookup *before* calling `enqueue()`,
  so a test awaiting `flush()` right after dispatching the key could miss the not-yet-
  queued task. Fixed by making the listener itself synchronous and enqueueing
  immediately, with the async lookup and the actual toggle running inside the queued task.
- **Two wrong test expectations, both hand-computed mastery arithmetic:** Task 5's and
  Task 12's mastery tests both had a `3 < 4` case mislabeled "met" in a comment; the
  implemented (and, elsewhere, self-consistent) criterion is `achieved >= target`.
  Corrected both to match the code, not the other way around.
- **One test-only selector bug (Task 9):** "the type selector offers exactly two types"
  queried `.field-type option` across a whole objective block, but each of the 3 preset
  fields has its own `.field-type` select, so it matched 6 options instead of 2. Narrowed
  to one field row.
- **Task 14 Step 2's "expect 9 sections" is stale**, not a bug I fixed — the plan's own
  Tasks 12 and 13 add `ui.aggregation` and `ui.backup` as new sections beyond the
  10-row table the plan started with. Actual count is 12, correctly ordered by
  dependency (`grep -n 'SECTION:' slp-tracker.html` to see them). Not worth "fixing" —
  it's just a stale expectation in a verification step, and the real check (no stray
  network calls) passed clean.

Every fix above has a code comment at the fix site explaining the *why*, not just the
*what* — read those before touching the render loop or the save queue.

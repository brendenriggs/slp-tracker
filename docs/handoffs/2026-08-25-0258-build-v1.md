## Verify before acting

**One open question, and it gates every future release. Answer it before writing the
storage layer.**

Is IndexedDB data on a `file://` page keyed to the **shared `file://` origin** or to the
**individual file path**? If it is the path, then every time an updated copy of the app
is sent to her, **her data is gone**, and export/import has to be part of the release
process from day one.

**This does not need her laptop.** It is Chromium's origin model, same on Linux. Test it
locally in about a minute:

1. Open `storage-probe.html` in Chrome, press **Save a test note**, note the token.
2. Copy the file to a different folder (`/tmp/`, a subfolder, anywhere).
3. Open the copy. If the same token comes back, updates are safe.

Record the answer in the probe-result doc either way.

## What was settled this session

The storage probe ran on her actual district laptop (Windows, Chrome 151). Full results
and reasoning are in `docs/superpowers/specs/2026-08-25-storage-probe-result.md` — read
it, don't re-derive. The short version:

- **IndexedDB, localStorage, File System Access, and stored-handle reuse all work from
  `file://`.** The architecture stands. ~10 GB quota.
- **`persist()` was denied.** Storage is evictable and "Clear browsing data" wipes it.
- **Decision (Brenden): accepted.** Backup is manual — she saves to a file. No automatic
  mirror in V1.
- **Build the backup button on the File System Access handle, not a download.** The
  handle proved reusable with no permission prompt, so she picks a file once (ideally in
  her Google Drive for Desktop folder) and every later press writes straight back to it.
  Same effort as a download, far better ergonomics, and Drive carries it off the laptop.

Repo housekeeping: the project moved from `dev/claude/slp-tracker` (an untracked scratch
folder) to `/home/brenden/dev/slp-tracker`, and is now its own git repo on `main`.

## Things a fresh agent will get wrong without being told

**It must stay one self-contained HTML file opened by double-click.** No build step, no
npm, no bundler, no CDN, no framework fetched at runtime, no network calls of any kind —
it runs on a district machine with student data nearby. If you reach for React and Vite,
you have already broken it. Vanilla JS in one file, clearly sectioned.

**She is never at a computer during a session.** She charts on paper and transcribes
later. This is keyboard-first *batch entry*, not live capture. This fact already killed
one complete screen design.

**Pre-filled field defaults must not count as data entry.** See the callout in spec §4.
This is the subtle bug that will otherwise ship: a pre-filled target that was never
touched must not be recorded as an observation.

**Progress is charted per objective, over time — never across objectives.** No
normalization, no comparable scales. Each objective owns its chart.

**Exactly two field types: number and text.** Not three. "Qualitative" means free text.
Resisting a third type is what keeps this from becoming a form builder (spec §9).

**Marking absent is one tap plus a keyboard shortcut.** No free-text parsing, no
inferring "absent" from what she typed.

**She will never use git, ever.** This repo is Brenden's version history alone. Delivery
to her is one HTML file she double-clicks — which is precisely why the origin question
above matters.

**Do not run anything on her machine without asking.** She is the end user, not a test
environment, and testing has to be scheduled around her.
